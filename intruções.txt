CONTEXTO DO PROBLEMA

Estou usando uma página de vendas hospedada em Vercel e atualmente tenho uma implementação própria de Meta Pixel + Conversions API (CAPI).

Também existe o script do UTMify na página.

Ao testar a página no Meta Events Manager, estou vendo vários eventos Processados e Desduplicados para a mesma ação.

Por exemplo, no evento InitiateCheckout, o Events Manager mostrou várias entradas com a mesma identificação:

checkout:premium:moldes_0f366440-014a-4f77-9dac-8ecf83387417

Algumas aparecem como:

- Servidor → Processado
- Servidor → Processado
- Servidor → Desduplicado
- Navegador → Desduplicado
- Navegador → Processado
- Servidor → Desduplicado

Também acontece algo semelhante com ViewContent e SubscribedButtonClick.

A análise da implementação indica que provavelmente existem dois sistemas fazendo tracking da Meta simultaneamente:

1. Minha implementação própria:
   Browser Pixel
   +
   Server-side CAPI

2. UTMify:
   script próprio de tracking
   +
   eventos automáticos
   +
   possível envio adicional de eventos para a Meta

O objetivo NÃO é remover o UTMify da página.

Quero continuar usando o UTMify para UTMs, atribuição e funcionalidades relacionadas.

O objetivo é impedir que o UTMify e minha implementação própria fiquem disparando os mesmos eventos da Meta em paralelo.

OBJETIVO FINAL

Quero que exista UMA única fonte de verdade para os eventos da Meta.

Minha implementação própria deve ser responsável pelos principais eventos da Meta:

- PageView
- ViewContent
- InitiateCheckout
- outros eventos explicitamente implementados no meu sistema

A estrutura desejada é:

Browser
   ↓
Meta Pixel
   ↓
event_id único

e, quando houver CAPI:

Browser
   ↓
Meta Pixel
   +
Server
   ↓
Conversions API
   ↓
mesmo event_id
   ↓
Meta faz a deduplicação Browser/Server

Ou seja, para uma única ação do usuário, eu quero algo conceitualmente assim:

1 ação do usuário

Browser → InitiateCheckout → Processado
Server  → InitiateCheckout → Desduplicado

OU:

Server  → InitiateCheckout → Processado
Browser → InitiateCheckout → Desduplicado

A ordem pode variar.

O que NÃO quero:

Browser → evento
Browser → evento
Server → evento
Server → evento
UTMify → evento
UTMify → evento

para a mesma ação.

EVENT_ID

A implementação atual já utiliza IDs como:

checkout:premium:moldes_0f366440-014a-4f77-9dac-8ecf83387417

e IDs semelhantes para ViewContent.

Quero preservar essa lógica de event_id.

O mais importante é garantir que:

Browser Pixel e Server CAPI, quando representam a mesma ação, utilizem o MESMO event_id.

Por outro lado, ações reais diferentes devem possuir event_id diferentes.

Não quero que você simplesmente crie um ID fixo para cada evento e faça todas as ações compartilharem o mesmo ID.

DUPLICAÇÃO

Também verifique se existe algum problema dentro da própria implementação customizada que esteja causando múltiplas chamadas do mesmo evento.

Por exemplo:

- múltiplos useEffect
- listeners registrados mais de uma vez
- componentes montados duas vezes
- callbacks executados mais de uma vez
- funções chamadas tanto pelo clique quanto por outro listener
- scripts carregados duas vezes
- Pixel inicializado mais de uma vez
- CAPI chamada duas vezes
- retry/reexecução sem necessidade

A implementação precisa garantir que uma ação real do usuário gere somente uma ocorrência lógica do evento.

IMPORTANTE SOBRE DEDUPLICAÇÃO

Não quero usar a deduplicação da Meta como desculpa para deixar vários eventos sendo enviados.

A Meta deve receber:

1 evento Browser
+
1 evento Server

quando Browser + CAPI estiverem sendo usados.

A deduplicação deve servir para unir Browser e Server, e não para mascarar múltiplos disparos do mesmo sistema.
