==================================================
DESCOBERTAS NO CÓDIGO
==================================================

Ao analisar a implementação atual, encontramos que minha implementação própria de ViewContent está estruturada assim:

trackEvent(
  'ViewContent',
  { section: 'Hero' },
  getViewContentEventId('Hero')
)

A função getViewContentEventId() cria IDs no formato:

viewcontent:<section>:<external_id>:<token>

e o token é armazenado em sessionStorage.

Depois o trackEvent() usa esse mesmo event_id para:

Browser:
fbq("track", "ViewContent", ..., { eventID: resolvedEventId })

e também para o envio server-side/CAPI.

Portanto, o fluxo pretendido é:

Browser ViewContent
        ↓
event_id X

Server ViewContent
        ↓
event_id X

Esse mesmo event_id deve representar a mesma ação e permitir a deduplicação correta pela Meta.

O código também possui proteções contra envio repetido usando sessionStorage e outras proteções server-side.

==================================================
PROBLEMA IDENTIFICADO COM UTMIFY
==================================================

No código/script do UTMify existe um ViewContentListener automático.

Ele possui comportamento semelhante a:

ViewContentListener.init()

e existe lógica que dispara:

automaticamente após determinado tempo, incluindo aproximadamente 8 segundos.

Também existe lógica automática baseada em scroll.

Ou seja, o UTMify possui mecanismos próprios que podem gerar ViewContent automaticamente.

Além disso, o UTMify gera eventos automáticos do tipo:

SubscribedButtonClick

com IDs:

ob3_plugin-set-...

Esses eventos aparecem no Meta Events Manager como:

Conectado automaticamente

e podem existir tanto no Browser quanto no Server.
